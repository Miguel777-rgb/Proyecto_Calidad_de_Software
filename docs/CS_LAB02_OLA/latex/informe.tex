\subsection{Modelo del diseño actual}

Las Figuras~1a y~1b (\ev{E-01}) modelan el módulo. El backend sigue cuatro capas: los routers de la API reciben la petición, los servicios coordinan el caso de uso, el dominio contiene la lógica pura (rachas, textos de los avisos) y los repositorios acceden a PostgreSQL mediante SQLAlchemy.

El flujo evaluado tiene dos pasos. Al evaluar las alertas, \cod{alert\_service.evaluate} detecta los episodios y \cod{notification\_service.create\_for\_events} registra un aviso pendiente por cada suscrito y canal. Lectura de las métricas:
\begin{itemize}
  \item \negrita{Complejidad.} Es baja en todo el módulo: la función más compleja es \cod{streaks.\_runs}, con 8, y ninguna supera 10. El problema del módulo no es la complejidad algorítmica, sino el reparto de responsabilidades.

def send_pending(session: Session, mailer: Mailer, *, limit: int = 200) -> SendSummary:
    pendientes = notifications_repo.pending_emails(session, limit=limit)
    enviados = fallidos = 0

    for notificacion in pendientes:
        mensaje = _mensaje(notificacion)
        try:
            mailer.send(
                Email(to=notificacion.user.email, subject=mensaje.subject, body=mensaje.body)

\subsection{R1: canales de aviso}

\negrita{Problema.} Que el sistema tenga dos canales está escrito en tres sitios: la tupla \cod{CANALES}, el cuerpo de \cod{send\_pending} y los filtros del repositorio. Incumple el principio abierto-cerrado: añadir un canal obliga a modificar código que ya funciona.

\negrita{Cambio.} Se introduce el contrato \cod{Channel} (Fragmento~\ref{frag:canal}, \ev{E-07}). Cada canal sabe entregar un aviso y declara si requiere envío: el correo sí; el aviso dentro de la aplicación no, porque el registro guardado ya es la entrega. \cod{ChannelRegistry} indexa los canales y \cod{default\_channels} es el único punto donde se decide cuáles tiene el sistema.

\begin{lstlisting}[float=htbp,caption={\ev{E-07}. Contrato de canal y canal de correo (\cod{services/channels.py}).},label=frag:canal]
class Channel(Protocol):
    @property
    def code(self) -> NotificationChannel: ...

    @property
    def requires_dispatch(self) -> bool:
        """Falso en los canales de consulta, donde el aviso guardado ya es la entrega."""
        ...

    def deliver(self, notice: OutboundNotice) -> None:
        """Entrega el aviso. Lanza una excepcion si falla; quien llama la registra."""
        ...


class EmailChannel:
    code = NotificationChannel.EMAIL
    requires_dispatch = True

    def __init__(self, mailer: Mailer) -> None:
        self._mailer = mailer

    def deliver(self, notice: OutboundNotice) -> None:
        self._mailer.send(
            Email(to=notice.recipient.email, subject=notice.message.subject,
                  body=notice.message.body)
        )


def default_channels(mailer: Mailer) -> ChannelRegistry:
    """Punto unico donde se decide que canales tiene el sistema."""
    return ChannelRegistry([EmailChannel(mailer), InAppChannel()])
\end{lstlisting}

El mismo criterio se aplicó al texto del aviso. El condicional de \cod{\_mensaje} se sustituye por la tabla \cod{COMPOSERS} de \cod{domain/notices.py}, que asocia cada tipo de aviso con su redactor. Un tipo nuevo se añade en esa tabla.

\subsection{R2: almacén, despachador y reloj}

\negrita{Problema.} La decisión de qué hacer cuando un envío falla está mezclada con las consultas a la base y con el reloj del sistema, así que no puede probarse de forma aislada.

\negrita{Cambio.} La lógica de envío pasa a \cod{NotificationDispatcher} (Fragmento~\ref{frag:despachador}, \ev{E-07}). El despachador recibe por el constructor tres colaboradores definidos como protocolos: el almacén de avisos, el registro de canales y el reloj. No importa directamente SQLAlchemy, FastAPI ni \cod{smtplib}. La implementación real del almacén, \cod{SqlNotificationStore}, vive en el repositorio junto con \cod{insert\_pending}, que concentra la inserción antes duplicada.

\begin{lstlisting}[float=htbp,caption={\ev{E-07}. Despachador con dependencias inyectadas (\cod{services/notification\_dispatcher.py}).},label=frag:despachador]
class NotificationStore(Protocol):
    def pending(
        self, channels: Sequence[NotificationChannel], *, limit: int
    ) -> list[OutboundNotice]: ...

    def mark_sent(self, notice_id: int, at: datetime) -> None: ...

    def mark_failed(self, notice_id: int, reason: str) -> None: ...


class NotificationDispatcher:
    def __init__(self, store: NotificationStore, channels: ChannelRegistry, clock: Clock) -> None:
        self._store = store
        self._channels = channels
        self._clock = clock

    def send_pending(self, *, limit: int = 200) -> SendSummary:
        codigos = [canal.code for canal in self._channels.dispatchable()]
        pendientes = self._store.pending(codigos, limit=limit)
        enviados = fallidos = 0

        for aviso in pendientes:
            try:
                self._channels.get(aviso.channel).deliver(aviso)
            except Exception as exc:
                self._store.mark_failed(aviso.id, str(exc)[:MAX_ERROR_LENGTH])
                fallidos += 1
            else:
                self._store.mark_sent(aviso.id, self._clock.now())
                enviados += 1

        return SendSummary(attempted=len(pendientes), sent=enviados, failed=fallidos)
\end{lstlisting}

\cod{notification\_service} queda como coordinador (Fragmento~\ref{frag:coordinador}): compone el despachador, fija el límite de la transacción y conserva sus firmas públicas; \cod{send\_pending} sigue existiendo y delega en \cod{dispatch\_pending}. Por eso las 34 pruebas de integración existentes no necesitaron cambios. El único router que cambia es \cod{routers/alerts.py}, en 3 líneas: el envío recibe los canales por inyección (\cod{ChannelsDep}, definido en \cod{api/deps.py}) en lugar del \cod{Mailer}. Los enumerados de canal, tipo y estado se movieron de \cod{db/models.py} a \cod{domain/notices.py}; la capa de persistencia los importa del dominio, y no al revés.

\begin{lstlisting}[float=htbp,caption={\ev{E-07}. El servicio como coordinador (\cod{services/notification\_service.py}).},label=frag:coordinador]
def notify_open_alerts_of(session: Session, user_id: int, laboratory_id: int) -> int:
    vigentes = alerts_repo.open_event_ids(session, laboratory_id)
    filas = plan_rows(
        ((event_id, user_id) for event_id in vigentes), NotificationKind.OPENED, CANALES
    )
    return notifications_repo.insert_pending(session, filas)


def dispatch_pending(
    session: Session, channels: ChannelRegistry, *, limit: int = 200, clock: Clock | None = None
) -> SendSummary:
    despachador = NotificationDispatcher(
        SqlNotificationStore(session), channels, clock or SystemClock()
    )
    resumen = despachador.send_pending(limit=limit)
    session.commit()
    return resumen
\end{lstlisting}

\section{Comparación mediante un escenario de cambio}

\negrita{Escenario.} «Añadir un tercer canal de aviso: una pasarela de mensajería externa a la que el sistema entrega cada aviso mediante una petición HTTP (\emph{webhook}).» Se eligió porque la SRS ya retiró un canal (el SMS) por su costo y un canal distinto del correo es el cambio más previsible del módulo.

class WebhookChannel:
    """Entrega el aviso a la pasarela de mensajeria externa."""

    code = NotificationChannel.WEBHOOK
    requires_dispatch = True

    def __init__(self, sender: WebhookSender | None) -> None:
        self._sender = sender

        if self._sender is None:
            raise WebhookNotConfiguredError
        self._sender.send(
            WebhookMessage(
                recipient=notice.recipient.email,
                subject=notice.message.subject,
                body=notice.message.body,
            )
        )

La diferencia más clara está en la complejidad. En el diseño actual cada canal nuevo añade ramas al bucle de envío, que pasa de 4 a 6; en el propuesto, la lógica del canal vive en \cod{WebhookChannel.deliver} y el despachador no cambia.

Ninguna de esas pruebas falla por un defecto: describen un comportamiento que el cambio modifica a propósito.

\negrita{Lo que el rediseño no resuelve.} En ambos diseños hace falta una migración de Alembic para el tipo enumerado \cod{notification\_channel} (H-11).

\subsection{Limitaciones de la evaluación}\label{sec:limitaciones}

\begin{itemize}
  \item \negrita{Base de datos fuera de Compose.} PostgreSQL~17.11 corrió en un contenedor desechable con la imagen de la API del proyecto, no en el servicio \cod{db} de \cod{compose.yml}; la versión mayor es la misma.
  \item \negrita{Configuración de plantilla.} Se usó \cod{.env.example} con secretos propios. Con los valores de la plantilla falla una prueba de configuración ajena al módulo.
  \item \negrita{Sin extremo a extremo.} No se ejecutaron las pruebas de Playwright.
  \item \negrita{Métricas por módulo.} Al tratar los módulos como clases no se calculó una métrica formal de cohesión (LCOM); la cohesión se evaluó con la lista de revisión.
  \item \negrita{Escenario prototipo.} El canal por \emph{webhook} no incluye la migración de la base ni una pasarela real; sirve para medir el cambio, no para desplegarse. La especificación elegida (canal siempre activo) determina qué pruebas existentes fallan.
  \item \negrita{Tiempos.} Dependen de la máquina; se informan como el rango de cinco ejecuciones.
  \item \negrita{Diagramas.} Omiten las dependencias hacia \cod{api.deps} y hacia módulos fuera del alcance; Ce las cuenta.
  \item \negrita{Puntuaciones.} El impacto y el esfuerzo de cada hallazgo son estimaciones del equipo.
\end{itemize}

\subsection{Aplicar el diseño a un nuevo escenario de cambio}

\negrita{Escenario.} «Avisar cuando una alerta vigente se intensifica», es decir, añadir un tercer tipo de aviso además de inicio y fin.

En el diseño propuesto el cambio se localiza así:
\begin{itemize}
  \item \cod{domain/notices.py}: un miembro nuevo en \cod{NotificationKind} y una entrada en \cod{COMPOSERS}.
  \item \cod{domain/messages.py}: la función que redacta el texto.
  \item \cod{alert\_service}: detectar la intensificación, igual en ambos diseños.
  \item No cambian el despachador, los canales, el repositorio ni el servicio de avisos. La prueba parametrizada \cod{test\_todos\_los\_momentos\_tienen\_texto} falla si se añade el tipo y se olvida su texto.
\end{itemize}

En el diseño actual habría que modificar además \cod{notification\_service.\_mensaje}. Esa función trata como aviso de fin todo lo que no sea un aviso de inicio, de modo que, si se olvidara actualizarla, el tipo nuevo enviaría el texto «terminó la alerta» sin que fallara ninguna prueba. El rediseño convierte ese error silencioso en un fallo visible.

\subsection{Proponer una prueba que evidencie comprobabilidad}

La prueba del Fragmento~\ref{frag:prueba} comprueba una regla de negocio de RF-03: un envío fallido no detiene a los demás. No usa base de datos, servidor de correo ni el reloj del sistema; los tres colaboradores son dobles en memoria. Forma parte de las 30 pruebas nuevas, que pasan en 0.04 s.

\begin{lstlisting}[float=htbp,caption={Prueba aislada con dobles (\cod{tests/unit/test\_notification\_dispatcher.py}).},label=frag:prueba]
def test_un_fallo_no_detiene_los_demas_envios(self):
    almacen = AlmacenEnMemoria([aviso(1), aviso(2), aviso(3)])
    canal = CanalQueFallaCon({2})

    resumen = despachador(almacen, [canal]).send_pending()

    assert (resumen.sent, resumen.failed) == (2, 1)
    assert canal.entregados == [1, 3]
\end{lstlisting}

La prueba equivalente del diseño actual (\cod{test\_un\_fallo\_no\_detiene\_los\_demas\_envios}, en las pruebas de integración) necesita seis \emph{fixtures}: cliente HTTP, sesión de base de datos, datos de muestra, configuración, cabeceras de usuario y buzón. Además no puede provocar que falle solo el segundo envío, porque el doble de correo falla siempre o nunca.

\section{Conclusiones}

\begin{enumerate}
  \item El módulo «Alertas y avisos» tiene un dominio bien diseñado (funciones puras, complejidad máxima de 8) y una capa de servicios con problemas concentrados: 8 de los 9 incumplimientos de la lista de revisión están en dos unidades.
  \item El problema no era la complejidad, sino la cohesión y la dirección de las dependencias. Ninguna función superaba el umbral de 10, y aun así el servicio de avisos reunía cinco responsabilidades y no podía probarse sin base de datos.
  \item Dos refactorizaciones resolvieron los cinco hallazgos priorizados sin modificar ninguna de las 442 pruebas existentes, que siguen pasando en el entorno del proyecto, con mypy estricto sin errores y una cobertura del módulo que sube de 95.63\,\% a 96.32\,\%.
  \item La mejora se midió con un escenario de cambio implementado en ambos diseños con la misma especificación: el canal nuevo toca dos módulos existentes menos y no aumenta la complejidad del bucle de envío. La misma medición mostró su límite: no reduce las pruebas que hay que actualizar.
  \item El rediseño tiene un costo, 16\,\% más de código y más indirección, y deja pendientes siete hallazgos, registrados con su decisión.
\end{enumerate}
